# AIG2C — MASTER INSTRUCTION FOR BUILDING THE KNOWLEDGE BASE

> **Назначение этого файла:** это стартовая инструкция для GPT/Codex/ChatGPT Desktop, который получает доступ к папке с документами проекта и должен быстро, последовательно и без лишнего расхода контекста построить качественную базу знаний для гражданского чат-бота и команды проекта.
>
> **Правило №1:** сначала полностью прочитай этот файл. Только после этого начинай открывать другие файлы.
>
> **Правило №2:** не читай всю папку хаотично и не пытайся держать все документы в контексте одновременно. Работай по этапам, веди реестр источников и открывай только релевантные документы текущего этапа.

---

## 1. Контекст проекта

Проект: **«Единая цифровая система приёма, маршрутизации, контроля и анализа обращений граждан»**.

Пилот: **город Жалал-Абад, Кыргызская Республика**.

Цель системы: дать гражданину единый цифровой канал для обращения через Telegram и WhatsApp, зарегистрировать обращение в основной системе, классифицировать его, определить ответственную организацию/подразделение, поддерживать SLA/статусы/историю, помогать оператору AI-подсказками и возвращать подтверждённый официальный ответ гражданину.

Ключевой принцип:

**AI не является владельцем бизнес-процесса.**

Основной Django backend остаётся источником истины по:

- Citizen;
- CitizenChannel;
- Conversation;
- Message;
- Appeal;
- AppealCategory;
- Organization / Department;
- Assignment;
- Workflow / status;
- SLA;
- Audit;
- AIJob / AIResult;
- официальным решениям и ответам.

AI может:

- определить язык;
- нормализовать текст;
- предложить категорию;
- предложить срочность;
- извлечь адрес/ориентир/сущности;
- оценить confidence;
- определить необходимость уточнения;
- предложить уточняющий вопрос;
- позже использовать RAG для ответов по официальным документам.

AI **не должен** самостоятельно:

- регистрировать Appeal;
- присваивать официальный регистрационный номер;
- менять статус Appeal;
- окончательно назначать организацию/исполнителя;
- закрывать Appeal;
- отправлять официальный ответ без подтверждения сотрудника;
- писать напрямую в основную PostgreSQL базу.

Она нужна позже для:

- BGE-M3 embeddings;

- поиска официального основания ответа.

## 4. Главные правила работы с источниками

### 4.1. Не придумывать факты

Нельзя добавлять:

- несуществующие телефоны;
- адреса;
- руководителей;
- компетенции;
- категории;
- нормативные основания;
- сроки;
- организационные связи;

если этого нет в источниках.

Если информации нет — записать это как `UNKNOWN` / `NEEDS_CONFIRMATION`.

### 4.2. Не путать «есть в документе» и «реализовано в системе»

Для каждого утверждения различать:

- `SOURCE_FACT` — прямо указано в документе;
- `DERIVED` — безопасно выведено из нескольких источников;
- `PROJECT_DECISION` — принято командой проекта;
- `IMPLEMENTED` — реально есть в коде;
- `PLANNED` — запланировано;
- `UNKNOWN` — нет подтверждения;
- `CONFLICT` — источники противоречат друг другу.

### 4.3. Не замалчивать противоречия

Если два документа дают разные:

- телефоны;
- адреса;
- руководителей;
- названия;
- подчинённость;
- компетенции;
- даты;
- нормативные ссылки;

создать запись в `CONFLICTS.md` и сохранить обе версии с источниками.

### 4.4. Сохранять происхождение каждого важного факта

Для каждого значимого знания сохранять минимум:

- `source_file`;
- `source_type`;
- `page` или `sheet` если возможно;
- `source_language`;
- `document_date` если известна;
- `extracted_at`;
- `status`;
- `notes`.

### 4.5. Не уничтожать исходные документы

Исходные файлы не менять.

Все результаты создавать в отдельной папке:

```text
knowledge_output/
```

## 5. Как читать папку без лишнего расхода токенов

Работай строго в этом порядке.

### Этап 1 — только инвентаризация

Сначала прочитай:

- имена файлов;
- расширения;
- размер;
- папки/архивы;
- даты изменения;
- названия документов.

Не разбирай содержимое всех файлов одновременно.

Создай:

```text
knowledge_output/00_SOURCE_INVENTORY.md
```

Таблица:

| ID | File | Type | Language guess | Topic | Priority | Duplicate candidate | Status |
|---|---|---|---|---|---|---|---|

Priority:

- P0 — официальный документ/справочник, критичный для маршрутизации;
- P1 — официальный документ, полезный для ответов;
- P2 — вспомогательный/исторический;
- P3 — дубль/неясный источник.

### Этап 2 — сгруппировать источники

Не открывать всё подряд.

Сгруппировать по темам:

1. органы власти;
2. муниципальные организации;
3. территориальная структура;
4. коммунальные службы;
5. образование;
6. здравоохранение;
7. культура;
8. транспорт;
9. социальные вопросы;
10. ЖКХ;
11. вода/канализация;
12. дороги/освещение;
13. санитария/отходы;
14. гражданская защита;
15. нормативные документы;
16. контакты;
17. справочники чат-бота;
18. прочее.

### Этап 3 — читать по одному тематическому пакету

Для каждой группы:

1. открыть главный официальный источник;
2. извлечь факты;
3. сравнить с дополнительными документами;
4. зафиксировать конфликты;
5. сохранить результат;
6. только потом переходить к следующей группе.

Так не нужно держать всю папку в активном контексте.

1. актуальный официальный нормативный документ с датой/номером;

5. внутренний документ проекта;
6. старый документ;
7. неидентифицированный файл.

Если нельзя доказать, какой источник актуальнее — `NEEDS_CONFIRMATION`.

## 16. RAG chunks

Файл:

```text
machine/rag_chunks.jsonl
```

Каждый chunk должен быть самостоятельным по смыслу.

Рекомендуемая структура:

```json
{
  "chunk_id": "...",
  "document_id": "SRC-001",
  "organization_ids": [],
  "topic": "...",
  "language": "ru",
  "title": "...",
  "text": "...",
  "source_file": "...",
  "page": 12,
  "sheet": null,
  "document_date": null,
  "valid_from": null,
  "valid_to": null,
  "verification_status": "verified",
  "tags": []
}
```

### Chunking rules

- не резать предложение пополам;
- не смешивать две разные организации в одном chunk без необходимости;
- сохранять заголовок раздела;
- chunk должен быть понятен без предыдущего chunk;
- избегать огромных кусков;
- не дублировать один и тот же текст много раз;
- не создавать embeddings здесь — только подготовить данные.

## 18. Обработка архивов ZIP

Не считать ZIP отдельным смысловым документом.

1. распаковать логически/просмотреть содержимое;
2. добавить каждый документ отдельно в source registry;
3. сохранять `container_archive`;
4. выявлять дубли с файлами вне ZIP.

Если один и тот же документ встречается несколько раз:

- выбрать canonical copy;
- остальные отметить `duplicate_of`.

## 19. Обработка Excel

Для каждого Excel:

1. перечислить sheets;
2. понять структуру колонок;
3. не объединять sheets вслепую;
4. нормализовать названия организаций;
5. проверить телефоны/адреса;
6. определить дубли;
7. фиксировать исходный sheet и строку/диапазон если возможно.

Excel часто может быть главным source-of-truth для:

- контактов;
- списка организаций;
- районов;
- ответственных лиц;
- тематических данных для чат-бота.

Но это нужно подтвердить содержимым, а не предполагать.

## 20. Что считается конфликтом

Записывать в `13_CONFLICTS.md`, если:

- одно название имеет разные написания;
- телефоны отличаются;
- адреса отличаются;
- подчинённость отличается;
- функции противоречат;
- старый и новый устав расходятся;
- разные документы дают разные сроки;
- разные источники называют разные организации ответственными за один вопрос.

Формат:

```text
CONFLICT-001
Entity: ...
Field: phone
Source A: SRC-012 → ...
Source B: SRC-044 → ...
Preferred value: UNKNOWN
Reason: невозможно доказать актуальность
Action: запросить подтверждение у мэрии
```

## 21. Knowledge gaps

Файл:

```text
14_KNOWLEDGE_GAPS.md
```

Это список того, чего не хватает для production RAG/routing.

Например:

- нет официального полного списка организаций;
- нет подтверждённых контактов;
- неизвестна граница компетенций;
- нет service zones;
- не определены часы работы;
- не подтверждены категории;
- нет официального SLA;
- нет актуального списка руководителей;
- отсутствует кыргызская версия.

Для каждого gap:

- что отсутствует;
- зачем нужно;
- какой риск;
- у кого запросить;
- желательный формат.

## 24. Контроль качества

Перед финалом проверить:

### Источники

- все значимые файлы учтены;
- ZIP раскрыты логически;
- Excel sheets учтены;
- дубли отмечены.

### Организации

- стабильные IDs;
- названия нормализованы;
- RU/KY не перепутаны;
- parent relationships подтверждены.

### Контакты

- нет конфликтов, скрытых молча;
- source provenance сохранён.

### Компетенции

- не выдуманы;
- есть источник;
- proposed отделён от verified.

### RAG

- chunk самодостаточен;
- нет бессмысленных повторов;
- есть source metadata.

### Routing

- `verified` только если правило подтверждено;
- inferred rules помечены `proposed`.

### Языки

- язык каждого chunk указан;
- отсутствующие переводы не выдуманы.
